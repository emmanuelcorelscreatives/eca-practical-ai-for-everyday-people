# Lesson 211 worksheet: select before building
## Outcome
Choose one recurring task with a clear trigger, stable input fields, an inspectable result, recognizable exceptions, limited permissions and a manual fallback. Explain concerns rather than inventing numerical scores.

## Exercise A — compare
Compare workshop enquiry → internal review item, photographed receipts → expense records, and varied inbox messages → automatic replies. For each, mark clear fit or concern for recurrence, trigger, predictability, result checking, consequence of failure and fallback. All may recur: recurrence alone does not select a winner. Why is the workshop candidate the smallest first project here?

## Exercise B — define the boundary
Fill every row of `selection-card-blank.csv`. Specify five required fields (Request ID, Name or group, Workshop topic, Preferred date, Contact method) and optional Notes. The trigger is one new workshop enquiry form response. The result is one saved internal review item with the fields preserved and status Needs review. State what a person still decides.

## Exercise C — inspect fictional inputs
The sample exercise's workshop scope is explicitly assumed to be Everyday spreadsheets or Phone photo basics; this is a self-created practice assumption, not a claim about an actual provider. Classify all six `workshop-enquiries.csv` rows as ordinary processing or human attention, and explain why. Do not silently repair missing or ambiguous values. An empty Notes field is allowed. A date is a preference, never confirmed availability.

## Exercise D — practice manual fallback
Choose WQ-001. Copy its six fields into `review-item-template.md`; set Needs review and compare field by field. Then inspect `review-item-checks.csv`: identify the changed date and inappropriate Approved status. Do not treat formatting as accuracy. Check one record per input; preserve its exact ID and every supplied value, including optional notes.

## Exercise E — readiness and permissions
Answer: Does it recur? Is the trigger clear? Are inputs predictable? Is the result checkable? Can it wait? Is there a fallback? Name the two required access categories (read submitted fields, create internal review items), and four excluded external/irreversible actions. Record assumptions (stable form fields, available reviewer, scope, supported connections) as unconfirmed until checked. Check current account/platform capabilities before future implementation; no specific product entitlement is promised here. If exceptions dominate, narrow or reject the candidate.
