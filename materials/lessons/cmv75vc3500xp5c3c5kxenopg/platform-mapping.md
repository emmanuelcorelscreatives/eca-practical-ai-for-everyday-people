# Mapping the exercise to a real no-code workflow

This is a behavior specification, not a claim about a current vendor screen, button name or subscription entitlement. The saved scene prompts specify Zapier and Google Sheets while the narration is platform-neutral; capture those actual products for any named-product demonstration. They are not prerequisites for the manual exercise. Do not build a lookalike or fabricate run history. Feature availability and labels can differ by account.

1. Receive one fictional case with a stable Case ID. Never silently fill missing input from a prior sample.
2. Build the fixed review proposal containing action, destination, final content, supporting context and validation status.
3. Record the human's explicit Approve or Reject against the reviewed version. If the proposal changes, review again.
4. Place the only test-spreadsheet action AFTER a filter that checks both Complete and Approve. Inspect actual alternate connectors and earlier steps.
5. Map the result row to the current case's fields. Keep a new training spreadsheet isolated from production.
6. Run the control first, then rejection and incomplete approval. Observe actual history and actual destination searches after each; do not substitute a generated diagram for execution evidence.

If the account cannot collect approvals, use the manual review-folder exercise in `worksheet.md`. Do not claim that a manual folder run demonstrated an automated vendor feature. No purchase, new privileged connection or real external action is needed for the manual exercise.

The optional Python model has extra safeguards for test-mode allowlisting, unchanged review versions and unique IDs. These illustrate safe exercise design, not asserted behavior of a vendor platform. Its outputs are local files only.
